# ADR-007：有序消息与原生重试

## 状态

已接受，用户于2026-10-26确认；尚待Phase E实现。

## 背景

现有Outbox保证业务与事件同事务落盘，但没有持久化事件序号或消费进度。规范要求同聚合严格顺序；单纯按时间扫描、队列FIFO或延迟后返回队尾均不能证明失败期间的业务消费顺序。本机现有RabbitMQ服务已核实为4.3.6。

## 决策

使用现有RabbitMQ 4.3.6的Quorum队列原生延迟重试，不安装延迟插件。新增持久化事件序号，同一aggregateId只有前序消费成功后才推进后序；前序重试超限进入死信时，该聚合保持阻塞，人工重放成功后恢复，其他聚合可继续。消费成功必须有数据库持久化证据，不能仅以Broker发布确认代替。

消息保留UUID eventId/messageId，序号仅用于顺序控制，不替换领域标识。序号分配与Outbox写入在Application工作单元内完成；发布、消费去重和重放均保持至少一次及Outbox边界。既有非空历史事件若无法从已持久化事实恢复顺序，应显式中止并交由人工确认迁移策略，不能以随机UUID或时间猜测因果顺序。

## 权衡

原生延迟重试减少额外转发与物理重试队列；需要RabbitMQ 4.3及以上。串行范围限制在聚合，死信期间牺牲该聚合后续事件的可用性以守住严格顺序。数据库进度与幂等凭据增加存储与事务开销；发布确认、消费成功、死信是不同状态，不应合并。

## 影响

修订SPEC-008/003的物理retry队列要求：原生重试保持在原Quorum队列的延迟状态，`.retry`仅保留为旧命名约定，不再要求另建队列。保留Topic、手动ack、数据库唯一去重及DLQ。后台调度仍在E03接入Quartz/ShedLock；E02只建立可显式调用的有界Relay，不提前添加无锁周期任务。用户同日进一步确认首期消费用于现有缓存失效补偿及ERP事件持久化留痕，不加入通知、财务等新业务副作用；两个订阅与独立DLQ已在E01.2实现。
