# 消息总线设计

## 1. 目标

构建稳定的异步通信能力，支持领域事件发布、系统解耦与最终一致性。

## 2. 总线选型（固定）

- Broker：RabbitMQ 4.3+；本地已确认使用现有4.3.6，见[ADR-007](adr/ADR-007-有序消息与原生重试.md)
- 交换机类型：Topic
- 投递语义：至少一次

## 3. 事件模型

消息体必须包含：
- eventId
- eventType
- occurredAt
- aggregateId
- payload
- traceId
- sequence（持久化顺序号，不替换UUID事件标识）

## 4. 可靠投递（强制）

- 事务写模型与事件写入 Outbox 必须同事务提交
- Outbox Relay 负责异步投递至 RabbitMQ
- 发送确认失败必须重试并记录

## 5. 消费治理

- 消费端必须手动 ack
- 消费逻辑必须幂等
- 失败消息在原Quorum队列使用原生延迟重试，超限进入DLQ；不另建物理retry队列
- 消费成功持久化后再ack；数据库唯一约束保证重复消息不重复产生副作用

## 6. 主题与队列命名

- exchange: stratum.topic
- routing key: 业务域.聚合.事件
- queue: q.业务域.事件
- retry queue: q.业务域.事件.retry（旧命名保留；当前使用Broker原生延迟状态，不声明物理retry队列）
- dlq: q.业务域.事件.dlq

## 7. 顺序与一致性

- 同一aggregateId按持久化序号严格消费，前序消费成功后才推进后序
- 前序进入死信后阻塞该聚合，人工重放成功后恢复；其他聚合继续
- 发布confirm不等于消费成功，不能据此放行同聚合后序事件
- 跨聚合流程通过补偿与状态机保证一致性

## 8. 可观测性

指标必须包含：
- 发布成功率
- 消费成功率
- 重试次数
- DLQ 积压

日志必须包含：
- eventId
- messageId
- traceId
- consumerGroup

## 9. 可执行验收

- 数据写入与事件发布满足最终一致性
- 消费端重复投递不会造成副作用
- 重试与 DLQ 流程完整可演练
- trace 可关联发布与消费链路
